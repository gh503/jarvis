# Native update staging and recovery

The updater implements a local **staging preflight**, not an automatic upgrade. It verifies an extracted candidate, records the exact old/new release identities, runs an explicit isolated readiness check, and abandons a failed stage. It never downloads, extracts archives, changes shortcuts, stops the production server, copies production data, or migrates databases. Keep both portable folders in place. The existing installer targets a fixed folder; activation is a separate operator decision.

Run with a trusted Node 24 executable and the updater from your trusted checkout/package. Do not execute the candidate's updater to decide whether that candidate is trusted.

```sh
node --experimental-transform-types scripts/update-native.ts verify /absolute/new-bundle EXPECTED_NEW_MANIFEST_SHA256
node --experimental-transform-types scripts/update-native.ts stage /absolute/new-transaction /absolute/old-bundle EXPECTED_OLD_MANIFEST_SHA256 /absolute/new-bundle EXPECTED_NEW_MANIFEST_SHA256
node --experimental-transform-types scripts/update-native.ts health /absolute/new-transaction
node --experimental-transform-types scripts/update-native.ts rollback /absolute/new-transaction
```

On Windows use absolute Windows paths and quote paths containing spaces. Positional hashes are lowercase 64-character SHA256 values. Each command prints JSON; failure exits nonzero. The transaction directory must not already exist and must be separate from both bundles. Choose a private local location outside production data. `health` and `rollback` serialize with the existing lifecycle lock.

## Trust and compatibility

Supply manifest hashes obtained through an independently chosen trusted channel. Computing a manifest hash from an untrusted extracted folder merely pins those bytes; it does not authenticate a publisher. Published archive SHA256 sidecars are not manifest digests. This CLI deliberately does not accept an archive digest as proof of an extracted directory. If your trust anchor is an archive checksum, verify it externally and extract using a trusted tool that rejects traversal, links and special files before establishing the manifest digest. The backup tar helper is not an application archive extractor.

Verification requires a clean stable `X.Y.Z` release, exact source tag and commit identity, the current host platform and architecture, and Node 24 runtime metadata. The new version must be strictly greater than the baseline; equal versions, prereleases and downgrades are rejected. Both baseline and candidate are pinned to their independently supplied manifest hashes. Every declared file must match size and SHA256, all regular files must be listed, and symlinks, hardlinks, special files, duplicate/case-colliding paths, unsafe paths and root `.env` files are rejected. Hashes establish byte identity, not code safety or a sandbox. Keep the folders protected from concurrent modification: verification and execution cannot defend against a malicious process running as your user. The manifest's runtime version is authenticated metadata, not an independently executed runtime identity check.

Package verification streams file contents with limits of 16 GiB per file, 64 GiB total payload, a 16 MiB manifest, 100,000 tree entries and a five-minute operation deadline. The package manifest lists files only; empty directories are permitted and are not an exact manifest inventory. Data snapshots instead record and verify directories exactly; see [snapshot validation](native-state-snapshot.md#validation-and-resource-bounds).

## Health and rollback behavior

Staging executes no candidate code. `health` explicitly authorizes execution of the verified candidate's bundled runtime and main module. It rechecks both folders before execution, creates fresh `health-data` under the transaction, and passes an allowlisted environment. It does not inherit `NODE_OPTIONS`, `NODE_PATH`, provider secrets, or `JARVIS_*` configuration. Home and data use separate private sibling directories (`health-home`, `health-data`) inside the transaction. Temporary files use `health-temp`; the runtime allocates its private IPC socket directory under canonical `/tmp` when the configured temporary path exceeds the Unix socket path budget, and removes that socket directory during shutdown. The data root is never the account home or temporary root; HTTP binds loopback on an ephemeral selected port and Ollama points to an unavailable loopback endpoint. A port collision fails readiness. Trusted candidate code still has the user's OS privileges; this is configuration isolation, not an OS sandbox.

Readiness uses authenticated runtime IPC and checks the expected loopback URL. An authenticated HTTP health request must report the candidate's exact version, source SHA and raw manifest SHA256; redirects, oversized responses and malformed metadata fail the check. These fields report installed metadata, not publisher attestation. The updater then requests authenticated shutdown and requires the directly spawned child to close with exit code zero and no signal. Cleanup waits are bounded; a child that fails to exit is terminated through that invocation's ChildProcess handle, never a stored PID. Readiness establishes startup viability only: it does not establish old database migration compatibility, provider operation, or packaged UI completeness.

The journal transitions from `staged` to `checking`, then `healthy` or `failed`. It records intent before launching candidate code. A failed health attempt preserves the journal, folders, and isolated data. `rollback` marks the stage abandoned, preserving all files for diagnosis; no production restore is needed because production was never changed. After interruption, rollback refuses to proceed while an isolated runtime still responds or owns its runtime lock. Inspect and explicitly stop that isolated runtime first; the journal cannot prove executable ownership after a crash. Do not delete a transaction while its candidate is running. Health cannot be retried in an existing transaction: rollback and create a new transaction.

Journal reads are limited to 64 KiB and reject linked files, malformed JSON and invalid UTF-8. Replacement flushes the temporary file before atomic rename and flushes the parent directory on POSIX; Windows does not flush the directory. This is not a claim of cross-platform power-loss durability or crash-atomic coordination across files. Interrupted creation may leave a transaction requiring manual inspection. There is no automatic garbage collection.

## Activation boundary

A `healthy` result is a reviewable staged version, not a switched installation. There is intentionally no `activate` command. The recommended [v2.0.42 unsigned preview](https://github.com/gh503/jarvis/releases/tag/v2.0.42) includes optional private external config binding: `install-native.ts --install --config ABS` persists the config filename in shortcuts and optional autostart arguments, and records that filename and the selected data directory in its ownership receipt. See [Optional private external configuration](native-install.md#optional-private-external-configuration) for file validation, permissions, precedence, and launcher commands. Installations without this opt-in retain the existing behavior. This is an editable path binding, not an immutable config digest or an automatic activation mechanism.

The installer still has no recoverable transactional switch API. Its receipt contains no config secrets and is not a snapshot or a recovery journal for a release switch. Editing the bound file can change the next launch's data directory; the receipt does not pin those file contents. The authenticated health endpoint reports installed release metadata, but this does not establish production data compatibility or a recovery contract. The isolated health check does not inherit the production external config binding. Automatically uninstalling/reinstalling shortcuts or running the candidate on old data could create a silent irreversible migration. Do not point a candidate at production data based solely on this preflight.

The **v2.0.42 portable packages** include the offline [data-only state snapshot CLI](native-state-snapshot.md), with explicit create, verify and restore-to-a-fresh-directory commands. This resolves the stopped data-filesystem copy, externally pinned manifest verification, and restoration-to-a-fresh-directory primitive. It includes all supported data files and empty directories, including secrets and application SQLite WAL, except the nine exact root ownership/coordination names documented there. Creation acquires launcher then runtime locks and fails for an active runtime without stopping it. External writers and legacy shell helpers that bypass those locks must be stopped. Restore never overwrites current data or activates a runtime, and successful verification does not establish logical/schema compatibility.

The **v2.0.42 portable packages** also include the offline [config-only snapshot CLI](native-config-snapshot.md), providing explicit capture, externally pinned verification, and restore into a fresh private directory for one validated external config file. It preserves exact original bytes, including secrets, comments, and quotes; it does not rewrite `JARVIS_DATA_DIR`. Create requires an explicit existing canonical data directory matching the config, acquires launcher then runtime locks, and requires other writers to be quiescent. Lock preflight may update operational files and data-root permissions/ACLs; source config validation remains read-only. Snapshot operations do not mutate the process environment. The source config parent and data directory must be disjoint in both directions; explicit config binding inside the data root remains supported, but cannot be captured by this config snapshot CLI.

The data-only and config-only primitives are separate operations, not an atomic coupled backup or a binding to a compatible baseline binary/schema. Config restore never overwrites an existing config or launches a runtime, and its unchanged data-directory setting still points to the old location. Neither primitive captures installer integration receipts or files outside its scope, such as externally referenced TLS material and models; relocation does not rewrite embedded absolute paths.

A future activation implementation must connect the authenticated release identity, selected production bundle, private external configuration, and corresponding data within a recoverable switch transaction. Coordinated binding snapshots, an installer integration transaction API with recoverable receipts, and compatibility/recovery contracts for every owned database and configuration format remain unimplemented. Ordinary backup import retains omitted destination state and is not an exact rollback. Full switching and schema compatibility recovery remain unimplemented; optional config binding and separate data/config restoration primitives do not make this a full automatic updater. Health and interruption recovery must be tested against these contracts. Existing production instance, data (including database sidecars), original config, and compatible binary remain the rollback baseline until those conditions are met.
