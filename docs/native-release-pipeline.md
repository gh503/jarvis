# Native release artifact pipeline

The `Native release artifacts` workflow follows a successful `ci` run on `main`. It resolves the published stable release whose remote tag points to that CI run's exact source SHA. It does not use the latest release or assume the package version equals the tag. This uses `workflow_run` because a release created by CI with `GITHUB_TOKEN` does not trigger a release-event workflow.

Each Linux, Windows and macOS runner checks out the resolved commit with tags, installs the lockfile, typechecks, runs the selected native tests, packages with explicit release version/SHA/tag, and tests the extracted archive using its bundled Node. The packager requires clean tracked files and an exact HEAD/tag match. The current matrix covers the architecture provided by each hosted runner; it is not a claim of coverage for every OS/architecture combination.

Publication is enabled through the repository Actions variable `JARVIS_NATIVE_RELEASE_PUBLISH=true`. Successful automatic runs may attach assets to the existing release only after all three build jobs pass. [v2.0.52](https://github.com/gh503/jarvis/releases/tag/v2.0.52) provides unsigned preview assets for Linux x64, Windows x64 and macOS arm64: an archive, SHA256 sidecar and provenance JSON for each target. These are published previews, not signed installers or a guarantee of stable production readiness. No workflow creates tags or releases. A manual dispatch requires an exact existing published stable tag and always produces **unsigned preview** Actions artifacts; it never attaches assets to a release. Older tags lacking this pipeline's scripts/tests cannot be rebuilt by this workflow.

The recommended v2.0.52 preview is published from verified source `ec015b75fd698b03d50896a8df939dfe24550b64`. [Release packaging and publication run 41486361114](https://github.com/gh503/jarvis/actions/runs/41486361114) succeeded and all nine assets are available. Separately, [native CI run 41485954079](https://github.com/gh503/jarvis/actions/runs/41485954079) passed all three platform jobs. These are distinct native-CI and release-publication results tied to this source; a newer tag or successful native CI alone does not establish a complete published asset set. The preview supports macOS/Windows `file_read`, `file_list` and `file_search` through the native helper, with at most 16 explicitly authorized read roots, UTF-8 text reads up to 1 MiB and secret-path filtering and private-key content rejection. It does not enable native writes, output workspace operations, artifacts, image inspection or Shell. Linux retains existing file writes and sandboxed Shell. Read-only Markdown skills were already supported on all three platforms. For source users, the optional `npm run native:build` helper build (Rust 1.94+ and the platform toolchain) is needed for both native file reading and skills; portable builds bundle the helper. These implementation boundaries do not replace representative interactive desktop validation, signing/notarization or manual upgrade requirements.

CLI source `e655` had [native CI 41490813672](https://github.com/gh503/jarvis/actions/runs/41490813672) still running. Neither result is evidence that those features ship in the recommended preview.

The shared lifecycle-lock SQLite guard, released in v2.0.40, rejects hardlinks, symlinks and nonregular entries in the main database and its journal/WAL/SHM sidecars before SQLite mutation. The main database identity must remain stable; normal SQLite sidecar removal and recreation are allowed. This is not a guarantee against hostile same-user filesystem races. The lifecycle-lock guard previously added 34 tests, including 16 sentinel checks.

v2.0.52 includes the offline [data-only snapshot CLI](native-state-snapshot.md), first released in v2.0.38, bounded streaming package verification, and Windows owner-validation alignment tested under an actual elevated token without relaxing private permissions. Package verification limits are 16 GiB per file, 64 GiB total payload, 16 MiB manifest, 100,000 tree entries and a five-minute deadline. Package manifests list files and permit empty directories; snapshot manifests separately require exact file and directory inventories. Snapshot creation requires a stopped runtime and quiescent other writers; verification and fresh-directory restore do not activate a release or prove schema compatibility.

First released in v2.0.42, the private [config-only snapshot CLI](native-config-snapshot.md) is included in v2.0.52 portable packages. It preserves exact original bytes without mutating the process environment, restores only into a fresh private directory, and retains the same `JARVIS_DATA_DIR`. The source config parent must be disjoint from the data directory in both directions; explicit config binding inside the data root is still supported but cannot be captured by this CLI. Config and data snapshots are separate operations, not an atomic coupled backup, full rollback, or automatic activation. External TLS files, models, and installer integrations remain outside the config snapshot scope.

First released in v2.0.45, the internal [stopped-data scope API](stopped-data-scope.md) lets trusted modules hold both lifecycle locks continuously across sequential optional config and data captures for one canonical root. Snapshot CLI behavior and manifest formats are unchanged; there is no `--scope` flag. This adds no aggregate recovery manifest, installed-version binding, or cross-version compatibility guarantee.

First released in v2.0.47 and included in v2.0.52, [native recovery sets](native-recovery-set.md) bind a verified baseline package identity to private config and data snapshots captured sequentially under one continuously held stopped-data scope. The aggregate captures baseline identity and child manifest digests, not installer integrations or a copy of the bundle. Verification requires the original baseline package to remain unchanged and available at its recorded path. This adds no schema compatibility guarantee, recovery-set restore, or activation command.

Every uploaded archive is labeled `unsigned` and includes the full source SHA in its filename. Adjacent SHA256 and provenance JSON files identify version, source tag, source SHA, platform, architecture and signing status. The archive's internal manifest records its payload hashes and runtime identity. These hashes detect content changes; they are not signatures and provide no independent publisher authentication. A stable GitHub release does not imply signing, notarization, SmartScreen reputation, or verified publisher status.

The publication job serializes by release tag, checks that the remote tag still points to the expected source, validates all three asset sets, and compares bytes of every colliding existing asset before any upload. Equal existing assets are skipped; different bytes fail. Upload never uses overwrite/clobber. GitHub has no atomic multi-asset upload: network/API failure can leave a partial set even after all build gates passed. A rerun can resume only with identical asset bytes. Native archives are not guaranteed reproducible (runtime updates, archive timestamps and runner images can change); preserve the original workflow artifacts when recovering a partial publication rather than deleting or replacing published assets.

Installed runtime version reporting reads the root packaged manifest, or the root package metadata for a source checkout. It ignores runtime release-version environment variables. Invalid present manifest metadata fails instead of silently reporting a source version. This metadata validation is not a signature-verification mechanism.
