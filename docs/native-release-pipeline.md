# Native release artifact pipeline

The `Native release artifacts` workflow follows a successful `ci` run on `main`. It resolves the published stable release whose remote tag points to that CI run's exact source SHA. It does not use the latest release or assume the package version equals the tag. This uses `workflow_run` because a release created by CI with `GITHUB_TOKEN` does not trigger a release-event workflow.

Each Linux, Windows and macOS runner checks out the resolved commit with tags, installs the lockfile, typechecks, runs the selected native tests, packages with explicit release version/SHA/tag, and tests the extracted archive using its bundled Node. The packager requires clean tracked files and an exact HEAD/tag match. The current matrix covers the architecture provided by each hosted runner; it is not a claim of coverage for every OS/architecture combination.

Publication is enabled through the repository Actions variable `JARVIS_NATIVE_RELEASE_PUBLISH=true`. Successful automatic runs may attach assets to the existing release only after all three build jobs pass. [v2.0.31](https://github.com/gh503/jarvis/releases/tag/v2.0.31) provides unsigned preview assets for Linux x64, Windows x64 and macOS arm64: an archive, SHA256 sidecar and provenance JSON for each target. These are published previews, not signed installers or a guarantee of stable production readiness. No workflow creates tags or releases. A manual dispatch requires an exact existing published stable tag and always produces **unsigned preview** Actions artifacts; it never attaches assets to a release. Older tags lacking this pipeline's scripts/tests cannot be rebuilt by this workflow.

The v2.0.31 preview is published from source `e4e3231562ce5b0502243e88e8fbfec85ba70d5a`, with all nine assets available after successful [native validation](https://github.com/gh503/jarvis/actions/runs/41445479068) and [release packaging and publication](https://github.com/gh503/jarvis/actions/runs/41445676791). These runs passed on all three platforms, including Windows packaged startup and shutdown with sealed private data. The preview supports macOS/Windows `file_read`, `file_list` and `file_search` through the native helper, with at most 16 explicitly authorized read roots, UTF-8 text reads up to 1 MiB and secret-path filtering and private-key content rejection. It does not enable native writes, output workspace operations, artifacts, image inspection or Shell. Linux retains existing file writes and sandboxed Shell. Read-only Markdown skills were already supported on all three platforms. For source users, the optional `npm run native:build` helper build (Rust 1.94+ and the platform toolchain) is needed for both native file reading and skills; portable builds bundle the helper. These implementation boundaries do not replace representative interactive desktop validation, signing/notarization or manual upgrade requirements.

Every uploaded archive is labeled `unsigned` and includes the full source SHA in its filename. Adjacent SHA256 and provenance JSON files identify version, source tag, source SHA, platform, architecture and signing status. The archive's internal manifest records its payload hashes and runtime identity. These hashes detect content changes; they are not signatures and provide no independent publisher authentication. A stable GitHub release does not imply signing, notarization, SmartScreen reputation, or verified publisher status.

The publication job serializes by release tag, checks that the remote tag still points to the expected source, validates all three asset sets, and compares bytes of every colliding existing asset before any upload. Equal existing assets are skipped; different bytes fail. Upload never uses overwrite/clobber. GitHub has no atomic multi-asset upload: network/API failure can leave a partial set even after all build gates passed. A rerun can resume only with identical asset bytes. Native archives are not guaranteed reproducible (runtime updates, archive timestamps and runner images can change); preserve the original workflow artifacts when recovering a partial publication rather than deleting or replacing published assets.

Installed runtime version reporting reads the root packaged manifest, or the root package metadata for a source checkout. It ignores runtime release-version environment variables. Invalid present manifest metadata fails instead of silently reporting a source version. This metadata validation is not a signature-verification mechanism.
